# v0.1.1 Thirty-Case Schema Stress Test

This note records schema-level observations after the reviewed 30-case validation set.

It is a **data-quality and methodology note**, not an analysis of national cybercrime prevalence.

## Source-stage composition

| Source stage | Cases |
|---|---:|
| Bail order | 26 |
| Appellate judgment | 3 |
| Interim order | 1 |

The heavy bail-order concentration reflects the current retrieval strategy and the fact that bail orders often reproduce unusually detailed incident and investigation narratives. It should not be interpreted as a property of social-engineering cases generally.

Sparse fields are **not removed yet**. Thirty cases are still too few to conclude that a variable is intrinsically unhelpful, and several sparse variables are conceptually important when they do appear.

## Structural pressure points

### 1. One incident row can compress several actor roles

A single incident may include:

- victim-facing caller or messenger
- account provider
- bank-account controller
- cash-out actor
- SIM/device user
- platform operator
- alleged organiser

The current incident-level row works for reconstruction but can blur actor-specific evidence.

**Pre-v0.2 question:** introduce an actor-level companion table linked by `case_id`.

### 2. One source can contain several claim types

Bail orders commonly contain:

- victim allegations
- police/investigation assertions
- defence claims
- judicial prima facie observations

The narrative notes preserve these distinctions, but a flat source row cannot encode every proposition and claim status.

**Pre-v0.2 question:** introduce a source-claim companion table linking proposition, source, claim type, and case.

### 3. Attribution should remain role-specific

The 30-case review repeatedly shows why an account, SIM, device, or money-flow link should not automatically be treated as proof of who performed the original social-engineering interaction.

The current `attribution_target`, `attribution_basis_*`, `attribution_strength`, `alternative_explanation`, and `primary_evidentiary_gap` fields remain useful and should be preserved.

### 4. Do not optimize the schema for easy completeness

Provider records, forensic examinations, authentication discussion, and chain-of-custody material are often absent from public case records. Their scarcity is itself relevant to understanding what public documentation can and cannot support.

## Decision before v0.2

The v0.1.1 schema is retained without breaking changes.

Before collecting approximately 50 cases, review whether to add:

1. `actors.csv`
2. `source_claims.csv`

Any such addition should be versioned and earlier cases should be migrated consistently.
