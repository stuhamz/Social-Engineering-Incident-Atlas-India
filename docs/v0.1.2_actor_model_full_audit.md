# v0.1.2 Thirty-Case Actor-Model Migration Audit

## Purpose

v0.1.2 adds an actor-role companion layer without changing the 30 reviewed incident records in `data/cases.csv`.

The incident table asks **what happened**. The actor table asks:

> **What specific conduct can the reviewed public evidence connect to a particular actor, role, or actor cluster?**

The migration is intended to prevent a bank-account, SIM, device, IP, payment or co-accused association from silently becoming attribution of the original social-engineering conduct.

## Scope

- Incident records retained: **30**
- Actor-role records: **90**
- Cases with actor records: **30 / 30**
- Minimum actor-role rows per case: **1**
- Maximum actor-role rows per case: **6**
- Cases with both an explicit victim-facing layer and financial layer: **23**

All actor records are linked back to the existing registered source IDs. No actor record changes the procedural status or guilt language of the parent case.

## Important migration findings

### 1. Actor-role, not person, is the correct unit

The second 20 cases confirm the pilot finding. A single identified person may have meaningful evidence for an account, withdrawal, OTP or device role while evidence that the same person made the original call remains weak or absent.

### 2. Financial attribution is often stronger than victim-facing attribution

Cases such as `SEIAI-0011`, `SEIAI-0016`, `SEIAI-0020`, `SEIAI-0021`, `SEIAI-0024` and `SEIAI-0025` contain substantially more developed money-flow/account evidence than operator-side evidence for the original social-engineering identity.

This is now represented structurally rather than only in narrative limitations.

### 3. `identity_resolution` must remain separate from `attribution_strength`

An identified account holder can receive a `limited` score for a broader alleged role. Conversely, an actor cluster can receive `moderate` support for a class of operational conduct where individual agent-to-victim mapping is incomplete.

### 4. Unknown operators are substantive data, not missing rows

For many incidents, the original WhatsApp/Telegram/phone persona is central to reconstruction even though no human operator is resolved. Omitting that actor would structurally privilege downstream suspects merely because they are named in court proceedings.

### 5. Platform/interface roles recur enough to retain

Fake investment/task applications and interfaces recur across the expanded set. `platform_account_operator` and `technical_infrastructure_operator` remain useful, but many such rows are `not_assessed` because public bail material describes the interface without provider-side control evidence.

### 6. One narrow score can legitimately differ from the incident-level summary

`SEIAI-0021` illustrates this. The parent incident remains conservatively `limited` for the applicant’s broader role, while the actor layer codes the narrower conduct of receiving, moving and cashing out funds as `moderate` because that specific financial conduct is more directly evidenced. This is not an inconsistency; it is the reason for the companion table.

### 7. `source_claims.csv` should still be deferred

The 30-case actor migration resolves the highest-value structural problem without requiring proposition-level annotation of every bail-order allegation, defence claim and judicial observation. A claim table may later become useful for a paper or intercoder study, but it is not required for v0.1.2.

## Data-quality rules retained

- A persona name is not a verified human identity.
- A bank-account holder is not automatically the fraud caller.
- A SIM subscriber is not automatically the device user at the relevant time.
- A device owner is not automatically the author of every communication on the device.
- A beneficiary is not automatically the organiser.
- A co-accused link is not standalone proof of conduct.
- Bail-stage allegations remain allegations.
- When two attribution levels are plausible, use the weaker one.

## Decision for next expansion

The actor schema is stable enough to retain for the next dataset expansion.

Before collecting substantially beyond 30 cases:

1. keep `data/cases.csv` as the incident-level table;
2. require actor-role coding for each newly reviewed incident;
3. run both structural validators;
4. monitor whether `role_primary` values remain sufficient;
5. defer `source_claims.csv` unless proposition-level source conflict becomes a repeated analytical bottleneck.

The next expansion should therefore test the schema on new cases rather than redesign it again immediately.
